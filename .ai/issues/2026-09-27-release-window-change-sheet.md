## Narrow ingress change, still needing an approved production responder

Use one owned, separately named file-provider YAML for an exact-host, non-redirecting 503 fence. It must have **four** target routers: HTTP and HTTPS for each of `allplan.net.tr` and `api.allplan.net.tr`, each at priority above the existing frontend's 9000 and the API's implicit priority. They all point to one pinned, non-customer-data maintenance responder on the existing shared application network. The responder returns HTTP 503 with `Retry-After`, no `Location`; health and image identity must be checked before admitting it into Traefik. Run it without application credentials, host ports, Docker socket or writable app mounts; use a read-only root, non-root user, dropped capabilities, no-new-privileges and bounded resources where its image supports them. Do not revive `allplan-maintenance-20260904`: it covers only the frontend host and historically redirects to the old site. Do not edit existing proxy files or restart the shared proxy as a shortcut.

The local Traefik 3.6.7 rehearsal proved a **single-file, same-name** change from service-only YAML to two exact-host maintenance routers and back: target-host responses 200 → 503 → 200, unrelated host 404, no redirect. The first attempt using `http: {}` was rejected by Traefik and is not acceptance evidence. Deleting the active file alone previously left the local watched provider at 503 for 10 seconds; therefore the withdrawal plan must retain a valid service-only file, trigger a provider readback and verify both public hosts before closing maintenance. Local test covered one HTTP entrypoint only, not public TLS/ACME, four production routers, live persistence or in-flight requests. The production responder image/config and four-router YAML are **not yet pinned or approved**; do not execute this paragraph as a command recipe.

## Abort and authority boundaries

If route withdrawal, old-writer drain, a pending side-effect job, mail TLS, migration, health, customer authorization or attachment checks are uncertain, **remain in maintenance**. Preserve all new PostgreSQL/R2/mail/Redis state and source originals; reconcile forward under ADR-022. Do not restore an older snapshot over newer accepted writes, restart the unsafe old image, bulk retry, erase queues or silently downgrade TLS. A long interruption is preferable to untracked customer-data loss and requires operator/user communication.
